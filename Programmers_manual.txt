CHAPTER 1 : SCRIPTS AND MAINTENANCE

The DIRAC programme system is maintained using the CVS and contains a number of shell 
scripts in order to extract a distribution version and to insert machine dependent lines.
Programmers should have some knowledge of these procedures, especially when adding or
deleting source files or directories. Below I will briefly describe the most important
features of the set up and indicate how essential files should be modified
when extending the programme with new modules.

1. Source and derived files.
Not all of the files that you see in the directory are residing in CVS. Take for instance
a freshly checked-out version of DIRAC and look for the Makefile. You will not find it !
The reason is that this file and others are generated by the pamadm script.

2. Optional modules.
The main reason to have a pamadm script is to be able to write different Makefiles
depending on how many "experimental" modules are included. These additional modules 
(like for instance dft) are in a separate directory and will not be
added when the program is distributed outside the authors group.

3. The pamadm script.
This script should always be run when new files or directories are added to the repository.
It creates all the Makefiles and the pam and export scripts (see below). 
The author of the new files should take care that this script is modified so that these
derived files contain proper reference to the new code. It should be rather straightforward
to do this by looking at the example provided by other (optional) modules.
DO NEVER EDIT THE MAKEFILES OR PAM DIRECTLY. They are derived files and are overwritten
by pamadm. The files to be changed are pamadm, configure, pam.in and the Makefile.in files.
Modules can be excluded from the release version by surrounding the
appropriate parts of code by preprocessor statements, e.g. :

#ifdef MOD_KRMC
         CALL TKRMCORB
         CALL SETDC2(0)
         CALL PSIOPT('MCSCF',WFCONV,WORK,LWORK)
         IF(DOANA) CALL PAMANA(WORK,LWORK)
#else
            CALL QUIT(
     &  'Second order KMCSCF optimization not included in this version')
#endif

This means that the calls are included only if MOD_KRMC is defined. Look in
pamadm for an existing module (e.g. DFT or KRMC) to see how this is done in
detail.

4. The configure script.
This script takes care of the machine dependent code. Please use this only for this 
purpose and DO NOT ADD MODULE RELATED INFORMATION. This was done in previous releases
of DIRAC and made things more complicated. The configure script contains references to the
GNU files configure.sub and config.guess that should not be edited. New versions should
rather be obtained from the Free Software Foundation. Please do only change configure.in,
e.g. when adding support for new operating systems (you should basically only put
in info about the best compiler and compiler options for DIRAC, which should be quite
straightforward).

5. The export script.
This script creates an export version (tar-tape) that can be used to distribute DIRAC
without or with only one of the optional modules active. 

6. The testlast script.
Use this script BEFORE checking in new code to verify that your modifications do not
affect other functionality. More documentation on this script is to be written.

7. The pam and pamq scripts.
The pam script is used to run DIRAC on various platforms. It takes care of setting up
a scratch directory, copying out restart files (if desired), cleaning up, etc.
Please modify this script if you hit a non-supported platform and check the
modification in so that others may also benefit from the work you did !
Pamq is basically a wrapper of pam that works with a number of queueing systems.

CHAPTER 2 : PROGRAMMING RULES AND HINTS

Dirac is for historical reasons largely written in FORTRAN77 but in the newer
parts of the code you may also see parts in C or Fortran90. Parallelism is
achieved via the MPI message passing library although some shared memory
parallelization via preprocessor statements of high-performance-fortran may
pop up in the future. The program also users other libraries like blas or
lapack for which a standard (but slow) implementation is found in pdpack. To
achieve optimal performance one should use optimized libraries at the linking
stage and use the included versions only when no optimized version is
available.

1. Use of languages
Do not introduce a new language before consulting the authors forum
at dirlab@dirac.chem.sdu.dk. New languages require compilers that may be
proprietary and consequently not be available to all authors (and users).

2. Use of BLAS and LAPACK
Try to avoid being creative when hitting a standard linear algebra problem
and look first in what is already available. The lapack and blas routines
available via the Atlas distribution provide a fast and stable implementation
for every platform. Try to use these first and if nothing is suitable check
for what is done in the gp directory as well. Some Dirac author may already
have done this before.

3. Hints for using Fortran90.
You may want to use Fortran90 features when modifying an existing routine.
Since Fortran90 does support almost all FORTRAN77 features this should be no
problem in principle. In practice you will hit some problems related to the
use of #include and preprocessor statments in the old code. A few things to
make life easier (search also the net typing fortran77 and fortran90 in
google, you will almost certainly find very relevant websites).

- The main difference between the old F77 code and new F90 code is the 
  source code format (the old code uses fixed form, F90 allows to use
  free form source code). However, it IS possible to use F90 features in
  fixed form (old F77) code - it only wont compile with a F77 compiler.  

- Use .F90 to identify free form source code files and use .F for fixed form.
  If you use F90 features in a .F file add a comment at the beginning of the
  file.
  The capital F in the filename extension tells most compilers to preprocess
  the files (I have tested pgf90 and the Intel compiler).  

- In F90 (and also as extension in g77) there is a INCLUDE keyword that
  could be used instead of the #include preprocessor statements - but please
  DO NOT use INCLUDE! The make system (makedepend) needs preprocessor
  statements to figure out the dependencies correctly !   

- Use IMPLICIT NONE in new code - it is much safer and the resulting code
  is easier to understand. And when you have to declare all variables 
  anyway - add a comment that explains what it does

- Do make use of the modularity that Fortran90 offers. We do, however, need
  more discussion to define where best to place common modules. Dirac meeting
  in 2004 ?

- Look at examples already done in f90 and read a good book to get acquainted
  with the language...

4. Fortran 90 and include files (F77 programmers - please also read this)

- Fortran 90 free form files may have problems with the include files for 
  several reasons:
  - comments work different in free form (! instead of something in column 1)
  - continuation works different (& at the end of the line instead of
    something in column 6 on the next line)
  - when you use IMPLICIT NONE, you get problems with undeclared variables 
    in the include files.

  For that reason:
  - only use ! to start comments in include files (all F77 compilers 
    understand this)
  - continuation use a & in column 73 of the first line and a & (nothing
    else!) in column 6 of the following line. This will work with both
    free form and fixed form when the file is included)
  - declare all variables explicitly, so that they can be used with
    IMPLICIT NONE

  There is a Python-script "reformat_includes" in the utils directory, that
  reformats include files according to these rules. When you write new 
  include files (or move old ones to the 'include' directory), please
  run this script on the files.     

- When you write new code and use F90, there should be no need to introduce
  new common blocks (and include files) - use modules instead, they are 
  much safer.


5. Remarks for F77 programmers (also applies for F90)

- There is no need mark to empty lines as comments. All Fortran compilers that
  are less than 20 years old can handle blank lines. 

- There is no need to to stick to 6 letter names anymore - I think all 
  F77 compilers support longer names as an extension and in a few places,
  longer names are already used. And when the 6 letter limit is dropped, there
  is no need to make names as short as possible anymore (the new limit is 31
  which allow quite long names). Please use this - it makes your code much
  easier to understand to someone else. 

- The same applies to uppercase/lowercase: It is not neccasary to use only uppercase
  anymore. Use uppercase and lowercase in a way that makes your code more
  readable. 


CHAPTER 3: DEBUGGING THE DIRAC PROGRAMME  

Here we present the simple example of an effective debugging of the DIRAC
program system. For this, the latest version of the widely used the GNU/gdb debugger is needed.
Make sure that the 'dirac.x' file is compiled with the -g flag.

Go to the working directory and
 make a link of the 'dirac.x' executable file there.
Ensure that the 'DIRAC.INP', 'MOLECULE.INP', 'gdb_demo' and of other needed files 
(e.g. 'DFCOEF') are there as well. The file 'gdb_demo' given in the $DIRAC/utils directory is the example
of using commands of the gdb debugger.

Run the 'dirac.x' in the debugging mode - type 'gdb dirac.x'. When the gdb command
line appear, type 'source gdb_demo' to read the source file
with demonstration commands for the gdb debugger.

Each time when you modify and compile DIRAC source files type 'file dirac.x'
in the gdb mode to reload latest changes in the executable. 

When you modify the 'gdb_demo'
source file apply the gdb command 'source gdb_demo' to reload it.

More GNU/gdb know-how is given at the web-page
http://sources.redhat.com/gdb/current/onlinedocs/gdb.html.

CHAPTER 4: CHECKING IN NEW CODE AND BUGFIXES

New code should always be checked in using the cvs system. The procedure is
the following :

1. Program whatever you want to add, taking care that it does not conflict
   with other functionality (unless you intend to replace e.g. a clumsy input
   routine by a better one). 

2. Create a test example in the directory tests (including a result directory and
   filter file). Do not commit this yet.

3. Check that your changed code passes the standard testset using the testlast
   script. If not go back to 1. or 2. (in rare cases the only change required is
   to change the input, output or filter file in the testset).

4. Run cvs update so that other peoples changes that have been commited while
   you were working on points 1-3 are included. These may conflict so you need
   to recompile and go back to step 3. An easy way to do step 4 is by using
   testlast -cvs=yes.

5.  If eveything works fine you are almost ready to commit. To keep the code
    and output clean we, however, also like you to check for debug (print)
    statements that you may have included. This is done by running cvs diff
    and verifying that this gives only the lines that you intended to change
    or add. Remove unwanted statements.

6.  Run commit from the directory in which the changed file(s) are located. If
    the commit commands tell you that there are changed files that you did
    not expect (since you did not change them) abort and check whether you
    really did not change them. The problem is that sometimes you inserted a
    temporary print statement that was removed later on but still gave the
    file a new date of creation. If so you can fix this by deleting this file
    and running cvs update once more. If not you continue the commit by
    editing the comment file, describing what you have changed. Don't forget
    to start these comments with your initials so that it is easy to see who
    did what.

7.  You and all other programmers will receive an email containing the text
    that you entered under 6. 

8.  The updated version will be run automatically on various platforms which
    may reveal bugs that you did not detect on your system. In that case one
    of the other authors will probably contact you to see how this problem
    (that is not your fault) can be resolved. If you messed up doing steps
    1. to 6. and created a bug you can also expect email, usually from me (LV).


The above is not meant to scare you from adding new functionality in DIRAC or
to commit bugfixes, just to make sure that everybody knows how one can work
together on a large program system like DIRAC.

Finally : Bugs are inevitable and will pop up when new types of calculations
are tried. We keep a database of known but not yet fixed bugs at 
http://radon.chem.vu.nl/cgi-bin/gnatsweb.pl
Login accounts are available for all authors, so please use this functionality
to register any bug that you encounter and - even better - have fixed.
